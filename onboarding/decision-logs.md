# Decision Logs: saving, submitting, and feedback

Keep one continuing file, `decision-logs/decision-log.md`, inside your course folder. It belongs in your own **private** `geap-103-portfolio` repository when you begin using GitHub in Week 3. Invite your teacher using the GitHub username they provide. Don't upload your work to the public course-materials repository.

## Starting in Week 2

1. Download the [Markdown template](../materials/decision-log.md), or use the copy in the [starter ZIP](../materials/geap-103-starter.zip).
2. Save it as `decision-logs/decision-log.md` inside your course folder.
3. Open it in a plain-text editor, such as VS Code or Notepad. Markdown is ordinary text with headings. You can also edit it on GitHub once your repository is ready.
4. Write Entry 1 about an actual interaction with a large language model (LLM), or identify the prepared response you evaluated. Keep the entry in your own words.
5. Add later entries to this same file. Give each entry a number and date. Save your changes and, once using GitHub, commit them with a short description.

You don't need GitHub set up to start. Use a local course folder or OneDrive until your repository is ready. If your Day 1 folder is called `Decision Logs`, rename it `decision-logs`. If you already wrote an entry in Word, copy its content into the Markdown template. Don't maintain a second Word log.

## Submitting a version

Saving or committing isn't the same as submitting. At each collection point:

1. Save and commit the current log. If you use local Git, push the commit to your private GitHub repository.
2. Open `decision-logs/decision-log.md` on GitHub in the file view, outside the editor. Press **y** to make a permanent link to that committed version, then copy the address. See [GitHub's permanent-link instructions](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files).
3. Paste that link into the Blackboard assignment for the collection point. Identify the entries you are submitting.
4. Make sure your teacher has accepted the repository invitation and can open the file. A private link doesn't grant access by itself.

The committed-version link identifies the work you submitted even if you edit the file later. Don't submit a moving `main`-branch link or a link to your computer's files.

| Collection | Entries | Purpose |
|---|---|---|
| Week 4 | 1–2 | Feedback: one strength and one improvement target |
| Week 8 | 3–5 | Feedback on how you used the earlier advice |
| Week 11 | Eight selected entries, each with a self-assessment | Final submission; entries 6–8 are assessed summatively |

Use the dates for your section in Blackboard. The [Wednesday schedule](../schedules/fall-2026-wednesday-14-meetings.md), [Monday schedule](../schedules/fall-2026-monday-12-meetings.md), and [delivery ledger](../admin/delivery-ledger.md) give the course dates. The existing 30% weight and [rubric](../admin/rubric-decision-logs.md) still apply.

## If GitHub is unavailable

Keep the same Markdown file locally or in OneDrive, make a dated backup, and upload the `.md` file to the Blackboard assignment at the deadline. Tell your teacher which step is blocked. When access is available, add the same working file to your private repository. You don't need to keep two separate portfolios.

## Teacher setup and privacy

- Confirm approved institutional use of GitHub for assessed student work. Private visibility alone doesn't establish approval. Until this is confirmed, use the local/OneDrive and Blackboard fallback.
- Give students your GitHub username, accept their invitations, and check access before the first collection.
- Create the three Blackboard collection points. Accept a committed-version link or the same `.md` file on the fallback path.
- Read the submitted version, not whatever happens to be latest. Return assessment feedback and grades privately through Blackboard. Ordinary task discussion can use the private repository, but grades and confidential feedback don't belong in commits, issues, or pull requests.
- Keep passwords, identification documents, grades, needs-assessment responses, other people's personal information, and raw private chat or recording data out of repositories. Use short, non-sensitive prompt excerpts and examples.
