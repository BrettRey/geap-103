## How the course would work
Students work through a common sequence of increasingly demanding tasks, individually, in pairs, or in small groups. The teacher circulates, helps with difficulties, and talks with students about their work. Students resume where they left off at the next meeting. As they become competent, they begin projects of their own and learn further skills as those projects require them.

The default environment is the GitHub Copilot app. The starting point is learning to direct an agent that can work with files. Students already bring experience with folders, email, and presentations; the tasks use that experience to introduce a different way of getting work done.

This draft sets out the progression and the support it needs. The next version would become the student task booklet, with practice files, short instructions, and optional hints. Task numbers indicate sequence, not class meetings. A task may take part of a meeting or continue across several.

The remaining twelve meetings provide about 29 working hours: 12:35–3:15, with a 15-minute break. An initial planning allowance is roughly 10–13 hours for the shared foundations and guided products, leaving 16–19 hours for increasingly independent work. These are untested design estimates; the early tasks should be shortened where students can already demonstrate the skill.

### Task 1 — Choose a model and start a conversation
Find the model selector, choose an available model, and ask a short question about a familiar topic. Locate the model's name and the conversation in the app. If another model is available, find how to switch to it. The immediate aim is to control the selection; comparing the quality of responses comes later.
### Task 2 — Give the agent a particular local folder
Connect the supplied practice folder and start an interactive session. Ask the agent to identify the files and read one named file without changing anything. Compare its answer with what is in the folder. Find where this session is working and distinguish that location from the original folder if the app has made a separate working copy.

The student should be able to show the teacher which folder the agent can use and point to the information it read.
### Task 3 — Access a repository
Connect the shared teaching repository and find the same practice material there. Read its instructions with the agent's help. Identify the repository on GitHub and its local working copy. Keep personal work in the student's own course folder/private portfolio, leaving the shared teaching source unchanged.

The practical question is where a change would appear: in the current working copy, in the student's online repository, or in the teaching repository. A local edit doesn't automatically update every copy.
### Task 4 — Ask for a file, then find and check it
Use the supplied club notes to produce a short email saved as a named file. Specify the audience and the details that must remain. Open the saved file outside the chat and check the date, time, reply deadline, and final question against the notes. Keep the source beside the result.

Begin the learning log here. In two or three sentences, explain what you can now do and show where the result is saved. The teacher can already assess the student's explanation of the task and one check they made.
### Task 5 — Request a precise change
Give the agent a bounded revision: for example, shorten the email while retaining all meeting details. Read the changes, check that the requested revision happened, and check that unrelated content stayed intact. Explain whether you will keep the new version and why.

Students who get a suitable first response don't need to invent a fault. Here the second request introduces a changed requirement, as often happens in real work.
### Task 6 — Save a version and recover earlier work
Save a named version of the work, make a small change, and recover the earlier version. Use the private portfolio's Git history where available, or the established local/cloud version-history alternative. Open the recovered file to confirm that it is usable. Distinguish saving, recording a version, and syncing it to GitHub.

The agent may guide the operation. The student must be able to identify what changed and show the recovered result.
### Task 7 — Continue in a fresh session
Close the current conversation and resume the task in a new one. Give the new session the relevant folder, source, current result, and a brief account of what should happen next. Check that it has the right material before allowing changes.

This completes the first foundation: students can choose a model, locate their work, direct a change, inspect the result, save it, and resume. Someone who can already demonstrate these actions can move through this section quickly.

## 2. Make useful products from supplied information
The booklet now gives a purpose, source material, and a description of a satisfactory result. Students increasingly compose their own requests. Optional hints remain available. Accuracy checks begin with specific questions and gradually become the student's responsibility.

Introduce selected [project ideas](../admin/sample-project-ideas.md) alongside these tasks. Students can start collecting ideas before choosing a project.
### Task 8 — Fill in a form
Give the agent a fictional person's profile and a simple registration form. Ask it to complete a copy of the form using only the supplied information. Open the completed file and check the mapping between the profile and the form: which information belongs in which field? Check names, dates, choices, and blank fields.

Then use a profile with a missing item. Decide what can be completed and formulate the question needed to finish it. The task introduces the distinction between finding information and guessing it. A later project could develop a plain-language form assistant.
### Task 9 — Turn an essay into a presentation
Read a supplied short essay, identify its main point and supporting ideas, and ask the agent to create an editable PowerPoint presentation for a stated audience. Specify a manageable length and what listeners should understand. Open the actual presentation and check its content against the essay.

Check whether shortening the essay has changed its meaning, dropped an important qualification, or introduced an unsupported claim. Preserve source acknowledgements. The result should be a usable presentation file, not just slide text in the conversation.
### Task 10 — Improve the presentation for its audience
Present a short section to a partner. The partner identifies one place they couldn't follow and explains why. Revise the wording, order, example, or visual accordingly. Check readable text, contrast, image descriptions where needed, and whether the slide supports the spoken explanation.

Now students are making audience-based decisions beyond following a supplied checklist. This can lead towards a cultural explanation, workplace training, or a presentation proposing the Humber monitoring project.
### Task 11 — Turn a table into an explanation
Use the supplied snack budget to produce a spreadsheet with a total and a useful chart, plus a short explanation of the largest cost and a possible saving. Check the total independently and trace chart values back to the table. Change one input and check what updates.

Students then explain the result to a partner who hasn't seen the source. Possible project connections include a spending tracker, event budget, business dashboard, or monitoring-project budget. More experienced students can use a larger table while practising the same checks.
### Task 12 — Compare two approaches to the same task
Try one short task with two available models, or compare the supplied outputs if access is limited. Keep the source and requirements the same. Decide which result is more useful for this task, using specific evidence: accuracy, completeness, clarity, suitability for the audience, or ease of revision.

Explain a choice, including any trade-off. One comparison supports a decision about these outputs; it doesn't establish a permanent ranking of models. Students may also decide that neither result is ready to use.
## 3. Work with less support and with other people
Students now receive less procedural guidance. They have to identify missing information, describe problems, and negotiate changes. Tasks 13 and 14 can use any of the products already made.
### Task 13 — Diagnose a problem and ask for useful help
Investigate a small problem in a copy of a practice product: a file that won't open, a wrong total, a missing source file, or a link that points to the wrong place. Describe what was expected, what happened, and what has already been tried. Read the error message or other evidence and use it in a request to the agent or another person.

Try an appropriate correction and check the result. If the problem remains, leave a clear handoff so someone else can continue. Existing problems can serve this purpose; prepared examples are available when needed.
### Task 14 — Hand over a change and negotiate a revision
Make a small improvement to a partner's practice product in an agreed working copy or branch. Describe the proposed change, receive a specific comment, and reply by accepting it, modifying the proposal, or explaining a disagreement. Keep a record of the change and the exchange through a pull request or the established tracked-change alternative.

Swap roles so that each student contributes a change and reviews one. Check that the owner can open and use the result. This prepares students to contribute different parts of a shared project.
## 4. Develop a project
Students can begin this section once they can manage their working files, direct and check a change, and complete one of the guided products. They can cover the remaining shared skills through relevant project work or return to the practice tasks. Everyone needs experience with the common skills; everyone needn't produce an identical set of practice files.

The teacher helps each student choose a next task that is demanding but workable. A student who needs more guidance can continue with supplied examples while a classmate is already adapting the same skills to a project.
### Task 15 — Choose a purpose and a first useful result
Choose a project from the ideas list or propose another. Explain who it is for, what it should help them do, and the first useful result you could make. This becomes the opening of the existing Goal Document. Choose one part to attempt first without having to settle the whole design.

Some possible routes are:

| Project direction | First useful result | Skills to develop next |
| --- | --- | --- |
| Spending tracker or business dashboard | Enter transactions and see a correct total | Data entry, calculations, charts, testing updates |
| Cultural story, teaching resource, or workplace training | One short section another person can use | Audience adaptation, media, accessibility, feedback |
| Form assistant or newcomer information tool | Explain and complete one small, checked section | Source checking, clarification questions, conditional instructions |
| Game or interactive experience | One playable interaction | Describing behaviour, testing choices, reporting faults |
| Humber North wastewater monitoring | A research brief, draft Facilities questions, budget structure, or demonstration dashboard | Research, data explanation, uncertainty, proposals, coordinated contributions |

The monitoring project could develop into a real institutional proposal. Students could take different components and combine them. Demonstration data would be public or explicitly simulated; actual campus sampling would depend on institutional agreement and qualified sampling/laboratory partners. Identifying the missing information and asking useful questions would be substantive project work.
### Task 16 — Gather and organize what the project needs
Collect the relevant sources, examples, data, and files. Explain what each contributes and what is still missing. Check consequential claims against the actual sources rather than accepting the agent's account of them. Identify material that shouldn't be shared with an AI service or other students.

Choose the next tool or technique because of a project need. A short teacher demonstration, a peer's explanation, or documentation can supply it. Students needn't complete a separate course in every tool they encounter.
### Task 17 — Build a first usable part
Describe the intended result and ask the agent to help produce it. Test it with a concrete example. If it fails, use the troubleshooting and revision skills already practised. Save a working version and document one decision that affected the result.

For a larger shared project, agree on the files or component each person owns and how the parts will connect. Each student keeps evidence of their own contribution and can explain it.
### Task 18 — Test it with someone else
Ask a peer or an appropriate intended user to try the product. Give them a real task and observe what happens. Compare what they understood or accomplished with what you intended. Record specific feedback, choose what to change, and explain the choice.

Testing should include a difficult or incomplete input where relevant: a blank form field, an unexpected answer, an absent file, or a value that changes a calculation. Check language, accuracy, and accessibility as well as whether the product runs.
### Task 19 — Revise, extend, and repeat
Revise the first part, add another useful capability, or improve its explanation and reliability. Repeat the build–test–explain sequence as the project develops. More independent students decide their own next steps; others work from a short list agreed with the teacher.

The ambition can grow with the student's competence. A change of direction is acceptable when the student can explain what they learned and why the new direction is more useful.
### Task 20 — Prepare a usable handover and explain the learning
Prepare the product, brief instructions, source acknowledgements, and a clear account of what works and what remains unfinished. Check access from the recipient's side. Select examples from the learning log that show how the student's requests, checks, explanations, or collaboration developed.

In a short individual conversation, demonstrate part of the work and explain a decision, a difficulty, and something you could now do in another context. The assessment should distinguish what the student understands and can communicate from what the agent generated.
## Learning documentation and English assessment
Use the existing continuing `decision-logs/decision-log.md`, broadening its purpose to include learning as well as decisions. Students add a short entry after a useful piece of work or a discovery, with a link or reference to the relevant file. Early entries might answer: What can I do now? What did I check or figure out? What do I still need help with? Later entries explain alternatives, evidence, and reasons for decisions.

This develops the log already in use. The private portfolio/Blackboard fallback stays in place, and confidential assessment feedback stays in Blackboard. Students may use AI to improve wording, but should be able to explain the entry and the work it describes.

The teacher begins short individual conversations during the first tasks, without waiting for a scheduled defence. Early questions ask students to locate, describe, and explain. Later questions ask them to compare, justify, diagnose, and negotiate. The student answers in their own words while showing the work; an AI-generated explanation alone is insufficient evidence of their English.

Keep a simple class list recording who has been heard and what to follow up. Speak with a rotating selection of students during each meeting, including those who don't volunteer. Return to students after feedback to hear what has improved. Students can continue working while waiting for a conversation; every task doesn't need teacher sign-off.

These observations would provide earlier and more frequent assessment and feedback. Whether they also replace any scheduled graded defences needs agreement when the assessment framework is revised. This draft doesn't change published weights, submission dates, or make-up arrangements.

The progression covers the seven [course learning outcomes](../CLOs.md): file/version management in Tasks 2–7; troubleshooting in 13 and subsequent project work; AI requests and evaluation throughout; technical communication in the conversations and log; digital products from Task 4 onward; and peer collaboration in 10, 14, and shared project work.
## Materials needed to make this teachable
Reuse the existing [shared practice files](../materials/week-02-shared-practice-repo/TASKS.md), project ideas, portfolio instructions, and log. Prepare a small fictional profile/form set, a short essay with source information, and a few recoverable problem examples. Each booklet task needs a clear result to aim for, a way to check it, and optional help. The early tasks need illustrated app instructions; later ones need concise briefs.

Test the file-producing tasks in the actual student setup before issuing them, especially editable forms, PowerPoint, and spreadsheet creation. GitHub documents model selection and project-based sessions, including local folders and repositories; the app's working location must be made explicit in the early instructions. [GitHub app quickstart](https://docs.github.com/en/copilot/get-started/quickstart-copilot-app); [agent sessions and model selection](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions).

While access is being resolved, students can practise requests and evaluation using the supplied files, available chat tools, and prepared responses. Partner demonstrations support practice; each student still needs an opportunity to demonstrate the relevant actions themselves. The course should preserve the existing access-neutral assessment alternatives.
